# Orca 3D hull order and mesh inspection

## Source and contract

OrcaSlicer v2.5.0 (`40ecc66f78ed72dc368e0c1ebe40d77f00cc8a19`) calls reentrant Qhull with dimension `3` and the sole option `Qt` in `src/libslic3r/TriangleMesh.cpp:1358–1434`. `deps/Qhull/Qhull.cmake` pins `v8.0.2.zip`, SHA-256 `a378e9a39e718e289102c20d45632f873bfdc58a7a5f924246ea4b176e185f1e`. The source archive used for this analysis matches that hash: Qhull **8.0.2**, release **2020.2** (`qhull_r 8.0.2`, 2020-08-31 in `src/libqhull_r/global_r.c:42–43`). The Nix package name `2020.2` is the alternate release designation, not a different version.

Replace the scaffold behind `ares-core/src/geometry/quickhull.rs::convex_hull_3d`, preserving the Rust public signature and returning `None` for the empty hull produced by Native on rank-deficient/failed input. Reproduce the ordered vertex bits, triangle indices, and outward winding for the same ordered finite `f32` input, not just the same polytope. `ConvexHull3d::normals` remains aligned to the ordered triangles for the Rust consumer; it is not an extra buffer returned by `its_convex_hull`. Do not deduplicate, sort, normalize signed zero, or otherwise preprocess the input independently of upstream.

## Required Qhull specialization

File references below are relative to the verified Qhull archive. The fixed configuration permits eliminating option parsing, I/O, tracing and operations only reachable through other dimensions/options. It does **not** permit replacing merge topology with a final grouping of coplanar triangles: a merge changes neighbors, the work queue, and the final ridge order even on exact boxes.

1. **Initialization and planes.** `libqhullcpp/Qhull.cpp:313–334` calls `qh_init_B`, `qh_qhull`, `qh_check_output`, `qh_prepare_output`. `libqhull_r/global_r.c:1138,1610–1638` sets `TRIangulate`, plus default `MERGING`, `PREmerge`, `ZEROcentrum`/`ZEROall_ok`; not `MERGEexact`, not `POSTmerge`. `poly2_r.c:2111–2189` calls `qh_maxmin`, `qh_detroundoff`, `qh_initialvertices`, `qh_initialhull`, then `qh_partitionall`. `geom2_r.c:1100–1349` picks extrema in axis order, starts with min X then max X, and extends by the largest absolute 2D/3D determinant on the extreme candidates, with the ordered wider search and early exit for a narrow/near-zero seed. It uses strict comparisons, not a longest segment or farthest Euclidean line point. `poly2_r.c:1491–1518,2244–2430` creates facets by omitting each descending-ID seed vertex in turn, with alternating `toporient`, assigns neighbors by omitted vertex, computes the inside point, and corrects simplex orientation/flags. Retain the real roundoff thresholds, 3D plane determinant and near-zero Gaussian path (`geom2_r.c:221,335,408`; `geom_r.c:845,971,1152,1250`).
2. **Point ownership and next apex.** `libqhull_r.c:1053–1119` scans initial facets in list order and the remaining points in input order; assigns at `qh_DISToutside`, keeps the strictly furthest point at the end of each outside set, then searches for owners of leftover points. Repartition from removed/merged facets (`:1326–1520`) in visible-list and set order. Keep the ordered neighbor search and fallback paths of `geom_r.c::qh_findbest`, `qh_findbestnew`, `qh_findbesthorizon`, preserving whether a threshold stops a search and where an equal-distance point is inserted. `qh_USEfindbestnew` can change as total merges exceed 50 or a new facet is nonsimplicial. Preserve near-inside bookkeeping, narrow-hull thresholds, and recomputation for `notfurthest`. After initial partition `qh_initbuild` calls `qh_furthestnext` once, moving the facet with greatest stored furthest distance to the front (`poly2_r.c:2003–2029,2187–2189`). In the main loop `qh_nextfurthest` (`libqhull_r.c:931–976`) advances `facet_next` past empty (or narrow/coplanar) sets and pops the last point of the first eligible set; it does not continue selecting a global farthest point.
3. **Cone and facet order.** `qh_addpoint` (`libqhull_r.c:176–298`) checks distance when required, discovers the visible region, attaches a cone, premerges, repartitions, deletes visible facets and handles queued vertex merges. `qh_findhorizon` (`:803–871`) moves the chosen facet to the list tail, then walks the growing visible suffix in discovery order, visiting stored neighbors in order. It distinguishes `dist > MINvisible` from the coplanar horizon `dist >= -MAXcoplanar`. `qh_buildcone` (`:401`), `qh_makenewfacets` (`poly2_r.c:2489`), and `qh_makenew_simplicial`/`qh_makenew_nonsimplicial` (`poly_r.c:621,726`) append each new facet in visible-facet order, then neighbor-slot order for a simplex or stored ridge order for a polygon. Preserve horizon parity, replacement and duplicate-ridge matching, not an unordered edge enumeration. `qh_appendfacet`, `qh_removefacet` and `qh_resetlists` also update the processing cursor when a facet moves. Arena indices can replace C pointers, but all observable traversals must follow the ordered sets and list updates.
4. **Merge during insertion.** `merge_r.c:75–99` first tries the zero-centrum fast check; if it fails, it marks duplicate ridges, merges coplanar horizon cycles, applies forced merges, then handles flipped facets and runs the initial and subsequent neighbor candidate queues and degenerate/redundant facet handling. `qh_compare_facetmerge` (`:895–904`) returns `-1` in both argument orders for equal keys, so its `qsort` call cannot define a portable order for such pairs. Verify whether equal-key candidate permutations affect the pinned reference before claiming parity beyond that build. Do not pass the inconsistent comparator to a Rust sort or fit a new key to the examples. The ordinary 3D path includes `qh_mergecycle_all`, `qh_mergecycle`, `qh_mergefacet`, `qh_mergeridges`, `qh_mergeneighbors`, `qh_reducevertices`/vertex replacement when applicable, and forced duplicate-ridge merges. The tentative cone and pinched-vertex retry in `qh_buildcone` require `Q14` and are not part of this path. Keep the order of ridge creation/removal and neighbor replacement, merge direction and destination tail moves (`merge_r.c:3004–3019,3490–3521`), and the replacement chain used for outside sets. `libqhull_r.c:70–109` does **not** execute either `qh_postmerge` branch for `Qt` alone in 3D (`qh_DIMreduceBuild=5`, `TESTvneighbors` off), but the final state/precision checks remain relevant to the empty-result behavior. Do not port undefined behavior or arbitrarily reject valid narrow/coplanar-horizon hulls.
5. **Triangulate and collect.** `io_r.c::qh_prepare_output` invokes `qh_triangulate` at `:1109`. `poly2_r.c:3482–3626,3671–3732` walks original facets in current list order, leaves existing simplex facets in place, and appends replacement triangles for polygons in stored ridge order using the first (highest-ID) vertex as apex. Null (repeated apex), mirror and original polygon facets are cleaned up in the upstream order. Children inherit the parent normal/offset under `Qt`. Facet/vertex IDs are creation counters, reset per hull; sentinel uses ID zero, initial vertices are allocated in seed order and prepended so the set is descending by ID (`poly2_r.c:2129,2174–2179,2425–2430,2924–2942`). New apex IDs advance that counter; a vertex ID is not the input index. The C++ `facetList()` (`Qhull.cpp:185–189`) traverses the current list from head to tail, not by ID. Orca visits each facet's stored descending-ID vertices, assigns packed output IDs on first encounter, then computes `(b-a) × (c-b)` in `f32`, dots it with the Qhull `f64` normal, and swaps indices 1 and 2 only for a strictly negative result. Do not port the C++ out-of-bounds path for a nontriangle.

The Rust port returns explicit errors instead of emitting an unchecked mesh when cone matching requires `qh_matchdupridge`/forced merges, triangulation detects a mirror requiring `qh_triangulate_mirror`, or a merge or final hull exceeds the precision bounds. It does not reject a hull merely because `qh.NARROWhull` is set. The mesh inspection, grounding and orientation paths use the fallible hull entry point; the original optional entry point is retained for callers that do not need to distinguish why no mesh was produced.

## Two-stage planes and CLI

`LayOnFace.cpp:19–33` and `Model.cpp:2811–2815` own the object hull: in volume order, compute a hull in each MODEL_PART's local coordinates, transform those hull vertices as Native's `TriangleMesh::transform` does, concatenate them, and hull the resulting points in that order. A lower-dimensional part whose local hull is empty contributes no points; do not substitute its raw vertices. Retain the common plane calculation for inspection and grounding. Follow `LayOnFace.cpp:33–158` for the first triangle normal in each connected group, ordered neighbors, world/plane transforms, float scaling and inverse affine, outline and centroid, and reverse-iterator area sort. Where an equal-area permutation is observable, reproduce the source library sorting operations of the pinned Native reference, not a new secondary key.

Register `--inspect-mesh` using `PrintConfig.cpp:12862`, `OrcaSlicer.cpp:1407–1425,6341–6352`, and `slic3r/Utils/MeshInspect.cpp:30–63`. Reuse the inspection load/transform pipeline. `ares-core` owns first-instance and mesh plane measurements; `ares-cli` owns the machine-readable stdout, argument checks and exit/report handling. Respect object/plane order, limit the displayed planes to eight but report total count, round only `area_mm2` as Native does, preserve signed zeros, and emit the Native schema and note. Do not alter `--info` or `--inspect-paint` behavior. Other Qhull modes (including joggled, Delaunay, Voronoi, half-spaces, arbitrary dimensions and explicit postmerge) and unrelated CLI features are out of scope.

## Feasibility and determinism

A pure Rust 3D specialization is feasible, but considerably larger than a facet sort on the current hull. The existing Quickhull seed, partition and face-vector enumerator must be replaced, not tuned. The high-risk work is the reachable merge/repartition/triangulation state machine and its exact ordered sets. Use typed indices into ordered arenas for vertices/facets/ridges, with explicit linked-list/cursor operations and dimension-fixed numeric kernels. Specialize only branches ruled out by the fixed configuration, not branches absent from the two example inputs. Preserve the pinned Qhull copyright/license and derivation notice with translated source.

* **Arithmetic:** `REALfloat=0` (`user_r.h:146`), so widen the ordered `f32` source exactly to `f64`. Keep the C evaluation grouping, including the left-associated `offset + x*nx + y*ny + z*nz` in `qh_distplane` versus the separately parenthesized dot in the determinant-plane validation. Retain normalization order, `sqrt`, division (do not replace with reciprocal multiplication), roundoff constants, comparisons and operation order for the Gaussian path. No FMA, fast math, approximate predicates, epsilons chosen from outputs, or signed-zero normalization. Keep the `f32` winding calculation and `LayOnFace` conversions at their upstream boundaries. Inspect reference build arithmetic if a bit discrepancy remains rather than assuming all C++ compiler/library combinations are identical.
* **Randomness:** Default `ROTATErandom=INT_MIN`, `JOGGLEmax=REALmax` and no `Qr`, `QRn`, `QJ`, or `Rn`. `global_r.c:1734–1767` seeds with `1` and samples/reseeds a PRNG as a configuration check, but the normal `Qt` computation consumes no random point, rotation, joggle, or distance perturbation. The `qh_RANDOMdist` example in `user_r.h` is commented out. A production RNG is not needed for this specialization.
* **WASM:** Scalar WebAssembly `f64`/`f32` operations and `sqrt` support the same separately rounded operations for finite values, including signed zero; no relaxed SIMD, implicit host math order, address-ordered traversal, or randomized map iteration. Audit any platform math beyond those operations, especially plane transforms, separately. A wasm32 build checks portability, not bit equality. Compare ordered mesh output indices and bit patterns against the pinned reference on host, and repeat the same comparison in a WASM runtime before claiming cross-target equality. Do not claim a common payload for NaNs or equivalence to Native builds using different contraction, floating-point environment, or library sorting rules.
