# Deterministic polyhole vertex trigonometry

## Source boundary

OrcaSlicer 2.5.0 (`40ecc66f78ed72dc368e0c1ebe40d77f00cc8a19`),
`src/libslic3r/PrintObject.cpp:209–235` (`create_polyholes`), builds each
regular circumscribed polyhole polygon by stepping a binary32 angle
`angle = rotation * i_poly + (float(PI) * 2 * (float)i_edge) / nb_edges` in
`[0, 2π)` and sampling each vertex at line 229 as
`Point(center.x() + new_radius * cos(angle), center.y() + new_radius * sin(angle))`.
In both pinned x86-64 OrcaSlicer binaries, the overload resolution lowers those
two calls to binary32 `cosf` and `sinf`, multiplies each result by binary32
`new_radius`, adds binary32 `center` coordinates, and rounds to `coord_t` via
`roundf`.

In `crates/ares-core/src/project_slice/hole_to_polyhole/polyhole.rs:55–56`,
`create_polyholes` currently delegates `angle.cos()` and `angle.sin()` to the
target math library. Replace only those two calls with the shared deterministic
binary32 kernel `crate::scalar_math::sincosf::sin_cos(angle)`.

## Scope and deferred behavior

Included in this slice:
- Evaluate both `sinf` and `cosf` at `polyhole.rs:55–56` through
  `crate::scalar_math::sincosf::sin_cos(angle)` so native and WebAssembly
  targets produce identical binary32 sine and cosine bits.

Unchanged and deferred:
- The `scalar_math::sincosf` implementation itself (unchanged; zero mismatches
  against host x86-64 glibc `sinf`/`cosf` across all 197,358
  `(nb_edges, multiple, i_poly, i_edge)` inputs for `nb_edges` in `3..=256`).
- The circumscribed-radius denominator `std::cos(PI / nb_edges)` at
  `PrintObject.cpp:226` (`polyhole.rs:46`), whose binary64 evaluation already
  matches bit-for-bit between x86-64 glibc and WebAssembly `libm` across
  `nb_edges` in `3..=50`.
- Edge-count derivation and capping (`hole_to_polyhole_max_edges`), rotation
  step and angle arithmetic, vertex multiplication/addition/rounding, clockwise
  winding normalization (`make_clockwise`), hole detection and grouping, and
  G-code formatting.

## Failure modes

Across `nb_edges` in `3..=50` (the default edge cap), WebAssembly `libm`
differs by one ULP from x86-64 glibc `sinf`/`cosf` on 175 reachable
`(nb_edges, multiple, i_poly, i_edge)` angles (21 untwisted, 154 twisted).
Multiplying a one-ULP difference by the scaled circumscribed radius and adding
the scaled hole center can move an integer polyhole vertex by one or two scaled
units (`1–2 × 10^-6 mm`). When the resulting perimeter segment lands near a
`0.0005 mm` three-decimal G-code formatting midpoint, WebAssembly emits a
different `X` or `Y` coordinate than native Ares and OrcaSlicer.

On the synthetic twisted 43-sided polyhole project
`tests/parity/hole-to-polyhole/twisted-43-sincos.3mf` (a `30 × 30 × 1.2 mm`
block with a centered 64-sided `10.75 mm` radius hole, build translation
`(110.000929, 110.000587, 0) mm`, classic single wall, `0.2 mm` layers, zero
infill, zero top/bottom shells, zero compensation, arc fitting off,
`hole_to_polyhole = 1`, `hole_to_polyhole_twisted = 1`):

- Layer `Z:0.2` (`i_poly = 0`, `slot = 0`, `i_edge = 6`, binary32 angle
  `0x3f6070f4`): x86-64 glibc and `scalar_math::sincosf::sin_cos` return cosine
  `0x3f23c19d`, whereas WebAssembly `libm` returns `0x3f23c19c`. OrcaSlicer and
  native Ares emit `G1 X132.031 Y133.447 E.0493`; unpatched WebAssembly emits
  `G1 X132.03 Y133.447 E.0493`.
- Layer `Z:0.8` (`i_poly = 1`, `slot = 3`, `i_edge = 39`, binary32 angle
  `0x40b74b2e`): x86-64 glibc and `scalar_math::sincosf::sin_cos` return sine
  `0xbf06f421`, whereas WebAssembly `libm` returns `0xbf06f422`. OrcaSlicer and
  native Ares emit `G1 X134.352 Y119.2 E.05329`; unpatched WebAssembly emits
  `G1 X134.352 Y119.199 E.05329`.

## Verification

1. **Browser witness** (`web/e2e/polyholeSincos.spec.ts`): slice
   `tests/parity/hole-to-polyhole/twisted-43-sincos.3mf` in Chromium through
   the public `ares-wasm` `sliceProjectPlateWithCatalog` entry point (falling
   back to the installed `systemPresetCatalog()` when no external preset
   catalog path is provided) and compare the entire G-code byte-for-byte
   against runtime OrcaSlicer in both official and seeded modes, ignoring only
   the single `; generated by` header line. Require runtime OrcaSlicer's output
   to include both `G1 X132.031 Y133.447 E.0493` and
   `G1 X134.352 Y119.2 E.05329`.
2. **Native CLI parity** (`crates/ares-cli/tests/orca_parity/option_coverage/hole_to_polyhole/vertex_trig.rs`):
   slice the same synthetic project with `ares slice` and require whole-file
   ordered byte equality (generator line excluded) against runtime OrcaSlicer,
   alongside the existing `option_coverage::hole_to_polyhole` suite in both
   official and seeded modes.
3. **Target and lint checks**: verify Rust formatting, workspace all-target
   Clippy, `wasm32-unknown-unknown` builds of `ares-core` and `ares-wasm`, and
   web formatting, lint, and type checks.
