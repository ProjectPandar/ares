# Concentric ironing: per-area entity assembly decides the emission order — discovery SPEC

Status: discovery record + proposed slice. Docs only: no source, no fixture, no
roadmap change.

**Conclusion (final shape):** the concentric G-code order is decided by *entity
assembly* — one `ExtrusionEntityCollection` per ironing area must reach the
per-region chain, and Ares collapses/segments them so the greedy chain has nothing
to reorder. The earlier clipper-ordering direction is withdrawn; see "Correction"
below.

## Problem

`ironing_pattern=concentric` is one of the two values the GUI and shipped
presets can produce (`PrintConfig.cpp:4298-4310`,
`enum_values = {rectilinear, concentric}`). With `ironing_type=top` on
`tests/parity/summary/time-cost.3mf` it is **not** byte-equal to Native.

Measured on main `9bbc63c9` (release build of that commit):

| oracle | Ares | Native | diff lines |
|---|---|---|---|
| seeded (`ORCA_REPLAY_SEED=0`) | 6,799,928 B | 6,799,948 B | 240 |
| official (canonical producer) | 6,799,928 B | 6,799,948 B | 240 |

Both oracles first differ at the same place (G-code line 257365): Native travels
to `X162.816 Y88.715` and irons the upper ring stack, Ares travels to
`X162.816 Y103.715` and irons the lower one.

### Fixture labelling (no masking needed)

The fixture sets `gcode_label_objects=0` — exactly the reachable value the
merged `alignedrectilinear` leg uses. With it, upstream emits the stable
`; start/stop printing object, unique label id: <n>` form instead of
`; printing object <name> id:<64-bit value>`, whose value varies per process.
With that setting the only run-to-run difference is the
`; generated by … on <timestamp>` line, i.e. exactly what the harness comparator
already normalises; no additional mask is introduced, and repeated Native runs
are byte-identical (verified: 0 diff lines between two fresh runs in each
oracle).

### Oracle determinism (both modes usable)

The official oracle **is** deterministic for this configuration when driven
through the canonical producer (`ARES_ORCA_BIN` = the official wrapper,
`ORCA_APPDIR`, `ARES_ORCA_NATIVE_BIN`, `ARES_ORCA_RESOURCES_DIR`; Native
parallelism 1). Repeated fresh runs with the harness comparator's normalisation (generator line
only):

- two fresh seeded runs: **0** differing lines;
- two fresh official runs: **0** differing lines.

An earlier note in this investigation claiming "official is non-deterministic"
was wrong: it came from invoking the native binary directly instead of through
the canonical wrapper environment, and from not separating `id:`/header lines
from geometry. No determinism problem is outstanding.

## What is established, and what is not

**Established by exact observation of the emitted G-code** (this is an exact
read of the per-area emission order, not an inference from travel):

- 1,243 concentric ring-stack blocks on both sides;
- the **multiset of blocks is identical** — same rings, same coordinates;
- identical **1,056-block prefix**;
- from block #1056 two same-shaped regions swap order:
  - Native #1056 = `(162.82, 83.27)–(168.26, 88.72)`, which appears in Ares at
    index **1214**;
  - Ares #1056 = `(162.82, 98.27)–(168.26, 103.72)` (same rings, dy = 15.00 mm),
    which appears in Native at index **1068**;
- only 16 of 14,584 ironing moves differ overall and all are relocating
  travel/link moves; the model time estimate shifts by 6 s.

**Not established: which intermediate vector first diverges.** The block order
proves the *per-area* order differs, but it does not by itself discriminate
between

1. `polys` accumulating in a different order (`Fill.cpp:1685-1697`
   `polygons_append` for top/bottom surfaces and, for `AllSolid`, the
   `stInternalSolid` appends), and
2. the order `intersection_ex` / the internal `union_ex` emits for the same
   input set (`Fill.cpp:1697`, `:1700-1702`),

because either can permute the final `ironing_areas` while leaving its content
unchanged. A previous draft asserted (2) from "pure permutation" alone; that
inference is invalid and is withdrawn here.

### Discrimination completed (which intermediate permutes first)

The G-code-order evidence above was not sufficient on its own, because
accumulation order and union output order both permute the same way. The
discriminator was obtained with temporary, uncommitted Ares instrumentation
(`ARES_IRON_AREA_DBG` at `fill_entities/ironing/areas.rs`, reverted; log
`evidence/ares-areas-order-instrumented.log`, analysis
`evidence/areas-order-analysis.txt`).

On the layer that the G-code diff shows reversed:

```
AREAS_IN  (accumulated areas = record.slices order)
  y sequence: +0.30, -14.70, -29.70, -29.70, -14.70, +0.30, +0.30, -14.70, -29.70   (mixed)
AREAS_OUT (Ares intersection_ex result = ironing_areas)
  y sequence: +0.09, +0.09, +0.09, -14.90, -14.90, -14.90, -29.90, -29.90, -29.90   (strictly Y-descending)
```

- Ares' produced order is **strictly Y-descending** and is **not** the input
  order (`OUT != IN`), so the permutation is produced by the
  intersection/union step, not by accumulation.
- Native irons the same two stacks in **Y-ascending** order (G-code
  `y=83.27` → model −32.7 before `y=98.27` → model −17.7).

Conclusion: the **first differing intermediate value is the ordered
`ironing_areas` vector**, and its owner is the clipper intersection/union
output ordering — upstream `union_ex` → `PolyTreeToExPolygons`
(`ClipperUtils.cpp:169-195`) — **not** `polys` accumulation
(`Fill.cpp:1683-1699`), and not `union_safety_offset` (not taken on this layer:
one region, no `stInternalSolid` fills).

Bounded scope of this conclusion: it decides *which* stage permutes. The exact
traversal rule that makes the ported engine emit the opposite direction is the
GREEN work. Reordering the result after the fact to match output is explicitly
forbidden; the fix must be in the ported traversal so the order falls out
naturally.

### Clipper1 ordering comparison (read-only, upstream `deps_src/clipper/clipper.cpp`)

The Clipper1 that Orca compiles is `deps_src/clipper/clipper.cpp`, included under
`Slic3r::ClipperLib` by `src/libslic3r/clipper.cpp`. The four order-bearing
places were compared line by line:

| role | upstream | Ares port | verdict |
|---|---|---|---|
| local-minima sort | `ClipperBase::Reset` `std::sort(m_MinimaList, lm1.Y < lm2.Y)` — Y ascending (`clipper.cpp:970-972`) | `minima.rs:28` `fixed_gcc_sort_by(&mut self.minima, a.y < b.y)` (Clipper1 policy `SORT_MINIMA_BY_X = false`, `round_policy.rs:32`) | same (Y ascending) |
| minima consumption | `InsertLocalMinimaIntoAEL` takes `m_MinimaList.back()` + `pop_back()` (`clipper.cpp:1492-1498`) | `minima.rs:54-60` `minima.last()` + `pop()` | same (largest Y first) |
| scanbeam | `std::priority_queue<cInt, cInts> m_Scanbeam` (`clipper.hpp:466-467`), default `less` = **max-heap**; `botY = m_Scanbeam.top()` then descending (`clipper.cpp:1109-1122`) | `engine.rs:200-203` `scanbeam.pop()`/`peek()` on a max-heap; same `botY`/`topY` loop (`engine.rs:170-186`) | same (max-heap, Y descending sweep) |
| output-ring creation | `AddOutPt` creates the OutRec on first `e->OutIdx < 0` (`clipper.cpp:2002-2017`); called from `InsertLocalMinimaIntoAEL` (`:1507`,`:1514`) and `AddLocalMinPoly` (`:1398-1444`) | `output/rings.rs:77-88` `create_out_rec` on first allocation; called from `insert_local_minimum` after `is_contributing` (`minima.rs:66-100`) | same shape |
| tree build | `BuildResult2` two passes over `m_PolyOuts`, append-only (`clipper.cpp:2801-2855`) | `polytree.rs:250-287` append by out_rec index | same |
| tree walk | `PolyTreeToExPolygons` root → holes → grandchildren recursion (`ClipperUtils.cpp:169-195`) | `polytree.rs:67-81` same recursion | same |

So the four candidate order sources are **not** where Ares differs, and the
earlier statement that "upstream is a min-heap" was wrong: the upstream sweep is
**Y-descending** (max-heap `top()`), exactly like Ares. The measured difference is
a different permutation *within* the sweep, i.e. which output rings get created
first for the same set of disjoint areas:

- Native order on the 9-area layer: grouped by **x** (largest x first), y
  descending inside each group, with the y direction alternating between groups
  (`(x=32.8,+0.3) (32.8,-14.9) (32.8,-29.9) (17.8,-29.9) (17.8,-14.9) (17.8,+0.3) …`);
- Ares order: grouped by **y** (`+0.09 ×3`, `-14.9 ×3`, `-29.9 ×3`).

This is now the open item: the specific rule that decides, for a single sweep
level, the order in which disjoint rings are created is still not pinned to a
source line. Candidates still to compare are the active-edge ordering used when
several local minima share one `botY` (`InsertEdgeIntoAEL`/`AEL` insert
comparator, `clipper.cpp:1492-1560` plus the `E2InsertsBeforeE1` tie-break at
`:2856-2870`) and the `ProcessIntersections`/`ProcessEdgesAtTopOfScanbeam`
sub-order. Per instruction, no fix will be attempted until that is located in
source; sorting the produced polygons afterwards is forbidden.

### Route (b) outcome: Native does not reorder after the clipper

The remaining question was whether Native's `ironing_areas` order is the clipper
scan order, or the `polys` input order (in which case a post-clipper reorder in
`Fill.cpp:1713-1731` or on the G-code side would be the culprit). Answered from
measurement, without needing a stack read on the stripped binary:

- Native's emitted order on the 9-area layer is **x-grouped, with y descending
  inside each group and the y direction alternating between groups**:
  `(x≈32.8, +0.3) (32.8, −14.9) (32.8, −29.9) (17.8, −29.9) (17.8, −14.9) (17.8, +0.3) (2.8, +0.3) (2.8, −14.9) (2.8, −29.9)`.
- The clipper sweep is Y-descending (max-heap `m_Scanbeam`, `clipper.cpp:1109-1122`),
  so a pure scan order for this set would be `y = +0.3, +0.3, +0.3, −14.9, …`
  i.e. y-grouped. Native is **not** y-grouped.
- Ares' `AREAS_IN` (proved position-for-position equal to Native's input order)
  has exactly the x-grouped/alternating structure Native emits.

So Native's `ironing_areas` follows the **input** order, not the scan order.
Because `Fill.cpp:1713-1731` is a plain `for (ExPolygon &expoly : ironing_areas)`
with no sort, and `eec->no_sort = true` (`Fill.cpp:1726`) forbids G-code-side
sorting, there is **no post-clipper reorder on the Native side**. Ares, by
contrast, *does* reorder (its `AREAS_OUT` is y-grouped).

Consequence: the deviation is inside the Ares clipper union/intersection output
ordering, not after the clipper — so route (b) resolves to route (a): compare
Ares' `create_out_rec` call order for this layer against the order the upstream
engine would produce. That comparison is the next step and needs the temporary
Ares instrumentation (or an equivalent runtime probe), which is not started
without approval.

### Two-pass structure verified; the deviation is already in pass 1

The upstream `intersection_ex(Polygons, Polygons)` is deliberately **two passes**
(ClipperUtils.cpp):

- `_clipper_ex` → `clipper_do_polytree` (`ClipperUtils.cpp:738-739` → `:642-655`):
  ```cpp
  if (auto output = clipper_do<ClipperLib::Paths>(clipType, subject, clip, fillType); !output.empty())
      return clipper_union<ClipperLib::PolyTree>(output, fillType);
  return ClipperLib::PolyTree();
  ```
- pass 1 `clipper_do<Paths>` (`:303-319`): `AddPaths(subject, ptSubject, true)`,
  `AddPaths(clip, ptClip, true)`, `Execute(clipType, retval /* Paths */, fillType, fillType)`.
  The `Paths` overload of `Execute` finalises through `BuildResult(Paths&)`
  (`clipper.cpp:2779-2798`), which walks `m_PolyOuts` in order and only skips
  `!outRec.Pts` and `cnt < 2` — no orientation grouping, no sort. (Note this is
  *more permissive* than `BuildResult2(PolyTree&)` at `:2801-2855`, which also
  drops closed rings with `cnt < 3`.)
- pass 2 `clipper_union<PolyTree>` (`:334-346`): a fresh `Clipper`, `AddPaths(output,
  ptSubject, true)`, `Execute(ctUnion, retval /* PolyTree */, fillType, fillType)`
  → `BuildResult2` → `PolyTreeToExPolygons` (`:169-195`).

Ares is the same two passes, same skip rules:

- `boolean_ex.rs:171-185` `execute_two_pass`: `execute_paths(operation, NonZero,
  NonZero)` then a fresh `Clipper` + `add_closed_paths(&paths, Subject)` +
  `execute_polytree(Union, NonZero, NonZero).into_expolygons()`.
- `output/fixup.rs:47-67` `build_paths`/`collect_out_paths` is `BuildResult(Paths&)`
  verbatim: iterate `out_recs` in order, skip `points == None`, skip `count < 2`,
  collect from `front.previous` backwards.
- `polytree.rs:250-287` `build_polytree` and `:67-81` `into_expolygons` match
  `BuildResult2` / `PolyTreeToExPolygons`.

So a "single pass" mismatch is **ruled out**: both sides run Paths→union(PolyTree),
with equivalent per-pass output rules.

### Where the order actually diverges (measured, route (a))

Temporary instrumentation (uncommitted, reverted; `ARES_CLIP_ORDER_DBG` in
`output/fixup.rs` and `polytree.rs`) printed the pass-1 and pass-2 sequences for
the target layer:

```
Ares PASS1_OUT  (BuildResult(Paths), i.e. m_PolyOuts order):
  [0](2.80,-0.30) [1](17.80,-0.30) [2](32.80,-0.30)
  [3](2.80,-15.30) [4](17.80,-15.30) [5](32.80,-15.30)
  [6](2.80,-30.30) [7](17.80,-30.30) [8](32.80,-30.30)      (mm, y-band groups, x ASCENDING inside a band)
Ares PASS2_TREE (after the union(PolyTree) pass):
  [0](32.80,+0.30) [1](17.80,+0.30) [2](2.80,+0.30) ... same y bands, x DESCENDING
```
Native, on the same layer, emits x-grouped with the y direction alternating
(`(32.8,+0.3) (32.8,-14.9) (32.8,-29.9) (17.8,-29.9) (17.8,-14.9) (17.8,+0.3) …`),
which is exactly the `polys` input order (`record.slices`), not a y-banded order.

Because Ares' **pass 1 already produces y-banded rings**, the divergence exists
before pass 2, i.e. in the sweep that creates the output rings, not in the
union(PolyTree) pass and not in `BuildResult`. Combined with the earlier finding
that all four order-bearing engine sites (minima sort, minima consumption,
scanbeam, AEL tie-break) match upstream line-for-line, the remaining candidate is
the **within-scanband order of local minima that share the same Y**:

- upstream orders them with `std::sort(m_MinimaList, lm1.Y < lm2.Y)`
  (`clipper.cpp:970-972`) — a comparator that only looks at `Y`, so equal-Y
  entries keep whatever order the unstable `std::sort` leaves them in, and
  `InsertLocalMinimaIntoAEL` then consumes `m_MinimaList.back()` (`:1492-1498`);
- Ares reproduces that with `fixed_gcc_sort_by(&mut self.minima, a.y < b.y)`
  (`minima.rs:28`) plus `minima.last()`/`pop()` (`:54-60`).

So the concrete rule to pin next is the **equal-Y tie-break produced by the
gcc `std::sort` emulation vs the layout the reference build actually gets**, since
that is the only remaining input to "which ring is created first inside one
scanband". This is a runtime/排序细节 question, not a missing pass and not a
`BuildResult` difference; it must be resolved before any fix, and reordering the
produced polygons afterwards stays forbidden.

### Correction: the order is decided on the G-code side, not by the clipper

The counter-argument is decisive and the earlier clipper direction is withdrawn: a
Native emission order that is x-grouped with the y direction alternating cannot be
produced by any Y-descending sweep (rings in different rows would have to be y-banded
for any equal-Y tie-break). So Native's G-code order is **not** its ironing_areas order.

Upstream G-code side (`src/libslic3r/GCode.cpp`):

- `:5466-5467` -- ironing is emitted **per island**, inside the island loop:
  `gcode += this->extrude_infill(print, by_region_specific, true);`
- `:6211-6234` -- `GCode::extrude_infill(print, by_region, ironing)`:
  outer loop `for (const ObjectByExtruder::Island::Region &region : by_region)`; builds
  `extrusions` = that region's `region.infills` filtered to `role() == erIroning`; then
  `chain_and_reorder_extrusion_entities(extrusions, m_last_pos.to_point())` (greedy
  nearest-neighbour reorder of the per-area ironing entities from the current position);
  then for each entity `eec->chained_path_from(m_last_pos.to_point())`, i.e. the inner
  chain runs even though the eec was built with `no_sort = true` (`Fill.cpp:1726`).

`Fill.cpp:1714-1731` is what makes that possible: **one ExtrusionEntityCollection per
ironing area** is pushed into `layerm->fills.entities`, so a region carries several eecs
and the greedy chain has something to reorder.

Ares has the same structure on the G-code side:

- `gcode_emit/motion/layer.rs:36` `for island in &mut layer.islands` -- ironing is emitted
  per island in the last per-region phase (`:105-116`), after walls, infills and
  infill-first walls, matching `GCode.cpp:5450-5468`.
- `layer.rs:56` splits entities into `region.ironing` via `is_ironing_entity`, mirroring
  the `role() == erIroning` filter.
- `layer.rs:148-151` -> `shared_reversals.rs:95-110` `chain_infill` -> `:59-93` `chain` ->
  `chain_and_reorder_entities_flips(entities, Some(start))` (the
  `chain_and_reorder_extrusion_entities` port).
- `layer.rs:160-165` applies `collection.chained_path_from(local_cursor(...))` per
  collection (the inner re-chain).

### Where it actually breaks: the per-area collections are collapsed

Temporary instrumentation (`ARES_IRON_EMIT_DBG` in `layer.rs`, reverted) printed
`region.ironing` per island/region:

```
IRON_EMIT region=0 entities=1 C1
IRON_EMIT region=0 entities=1 C1
IRON_EMIT region=0 entities=5 C1,C1,C1,C1,C1
IRON_EMIT region=0 entities=4 C1,C1,C1,C1
counts: entities=1 x56, =3 x12, =5 x6, =4 x5, =6 x4, =2 x3, =8 x2, =43 x1
```

The diverging layer is one of the `entities=1` cases: Ares hands the emitter a **single**
ironing collection holding a single entity. With one entity neither the outer
`chain_and_reorder` nor the inner `chained_path_from` can permute anything, so the emitted
order collapses to the area order -- exactly the y-banded order measured earlier
(`AREAS_OUT`). Upstream has one eec per area on the same layer, so the greedy chain from
`m_last_pos` produces the serpentine order seen in Native G-code.

Root cause: **the per-area `no_sort` collections that `make_ironing` pushes into
`fills.entities` are collapsed (merged) before the G-code side chains them**, not a clipper
ordering difference.

### Assembly chain trace (read-only, merge point located)

`fill_entities/ironing.rs` does push one `FillExtrusionCollection` per ironing area
(matching `Fill.cpp:1714-1731`), with `no_sort: true`. The collections then pass
through `project_slice/extrusion_islands.rs`:

- `:110-115` builds the island test order: `fixed_gcc_sort_by(&mut order, bounds[*l].area() < bounds[*r].area())`
  — ascending bounding-box area, the `slices_test_order` semantics of `GCode.cpp:4984`.
- `:117-139` walks `(region, collection)` pairs (`layer.collection_ranges` zipped with
  `layer.collections`) and assigns each to an island:
  - `let island = island_index(collection.first_point(), slices, &bounds, &order);`
  - `if collection.no_sort { islands[island].infills.push((region, source_order, FillCollection(collection))) }`
    else the collection is flattened into individual `Fill(entity)` entries.
- `:197-203` `island_index`: first slice in area-ascending order whose bbox contains the
  point *and* whose contour contains it, else `slices.len()` (the "last" bucket) — the
  same rule as `GCode.cpp:5062-5068` (`slices_test_order` + `point_inside_surface`).

So Ares keeps the per-area collection (`no_sort` → `FillCollection`), exactly like
upstream, and its island rule matches upstream. What differs is **how many of those
collections a single island's region ends up holding**:

```
ARES_ISLAND_DBG (temporary, reverted) on the fixture, layer with slices=9:
  161 assignments, of which 79 are no_sort (ironing),
  spread over islands {0, 1, 2, 5, 8}
```
and the emitter-side count from the previous probe was `region.ironing entities=1 C1`
for the diverging layer. I.e. the ironing areas are scattered across islands so that
each island's ironing region holds a **single** collection; `emit_infills` then calls
`chain_and_reorder_entities_flips` on a one-element vector (no reorder possible) and
`chained_path_from` on a single-entity collection (no reorder possible either), so the
emitted order equals the assembly order.

Upstream, the same layer's 9 ironing eecs must end up in **one** island's
`by_region[region].infills` for the greedy chain to produce the serpentine order, so
the remaining question is precisely: which island bucket each ironing area's
`first_point()` lands in, on both sides. Ares' rule is source-equivalent to upstream's
on inspection (`island_index` == `point_inside_surface` over an area-ascending order),
which means the discriminating input is the **collection `first_point()`** itself — the
first point of the area's first ironing polyline — and that is where Ares and Native
are known to differ already (pass-1/pass-2 first points differ, see the two-pass
section). This is the read-only boundary: the fix must make the ironing collections
land in the same island buckets as upstream, or keep them in one region list, but it
must not reorder emitted entities afterwards.

**GREEN boundary (precise, but pending one confirmation):** the change belongs in the
ironing/assembly seam — `project_slice/extrusion_islands.rs` island assignment for
`no_sort` fill collections (`:117-139`) and/or the region grouping consumed at
`gcode_emit/motion/layer.rs:42-59` — not in `fill_entities/ironing.rs` (which already
matches upstream), not in the clipper, and not in the emitter's chaining (which already
matches upstream). Confirmation still needed: the per-collection `first_point()` values
for the diverging layer on both sides, to prove the buckets differ for that reason
rather than because of a differing `slices` count.

### Confirmation run: first_point comparison (read-only, G-code only)

Matched every ironing block between Native (seeded, labels=0) and Ares by bounding
box, then compared the first extruded point of each matched area:

```
blocks native=1243 ares=1243
bbox-common blocks: 1225   (native-only 0, ares-only 0)
matched areas with SAME first point: 1213 ; DIFFERENT first point: 12
example of the 12:  bbox=(162.82, 98.27, 168.26, 103.72)
   native_first=(162.816, 98.269)   ares_first=(162.816, 103.715)   n=5/5
```

Reading:

- 1,213 of 1,225 matched areas start at the **same** point, so the ironing *start
  point* is not the differentiator (the hypothesis that the root cause sits in the
  ironing generation path is therefore **not supported** for this layer).
- The 12 differing areas are a pure **ring-stack direction reversal**: identical
  bbox, identical 5 segments, first and last point swapped. That cannot change an
  island bucket (same bbox), and it is a consequence of the inner
  `chained_path_from` starting from a different head position.
- Both sides are byte-identical through G-code line 257,365, i.e. every wall and
  perimeter of that layer matches, so the layer's `slices` partition is the same on
  both sides. Combined with the matched first points, the island buckets must also be
  the same — which contradicts the earlier "each island holds one collection ⇒ no
  reorder possible" reading of `entities=1`.

Open contradiction (recorded, not resolved): with identical areas, identical
`first_point` for 1,213/1,225, and identical `slices`, the assembly must produce the
same buckets, yet the emitted order differs. So the remaining candidate is **not**
the bucket content but the **order in which the buckets are visited / the
`m_last_pos` the chain starts from** — i.e. the island iteration and the per-island
starting head position, which is exactly what `chained_path_from(m_last_pos)` and the
outer `chain_and_reorder_extrusion_entities(extrusions, m_last_pos)` depend on. The
next read-only step must therefore compare, per island, the head position the chain
starts from on both sides (Ares: `local_cursor(state, geometry)` at the ironing phase;
Native: `m_last_pos` at `GCode.cpp:6211-6234`), not the island assignment.

### Head-position comparison (read-only, G-code derived) — first divergence pinned

Derived from the two G-code files (no probe, no GDB): per layer, the head position
before the first ironing block, the block sequence with bboxes, and each block's
first point.

- Layer `z=0.8`: both sides identical (same head `(100.789,150.612)`, 80 blocks,
  block-by-block identical).
- Layer `z=51.2` (the layer of the first G-code diff at line 257365): both sides have
  20,602 moves, the same 191 ironing blocks, the same head `(131.566,81.371)`, and the

Two structural corrections matter here:

1. The z=52 ironing phase is **one** entity — a single `FillExtrusionCollection` holding **182 closed
   rings** — handed to a chain call of `n = 1`. There is no list of eecs to reorder on this layer, so
   `chain_and_reorder_entities_flips` sees a one-element vector and `chained_path_from` returns it

   `n=20` measurement from the earlier round belonged to a different layer (layer index 45), not this one.
2. Because `f == l` for every path, each path is one closed ring, so ring start points are the only
   endpoints available and they are what the output order is made of.

Set comparison. Both G-code files share the same bed origin, so no coordinate conversion is needed for a
G-code-to-G-code comparison. Layer 52 was split into contiguity runs on both sides and each run was
reduced to `(min_x, min_y, max_x, max_y, len)`:

```

ares-only  : (162.816,103.565, 162.966,103.715, 2), (162.966, 98.419,...), (163.116,103.565,...)
```

i.e. a stack that sits at y≈98 on one side sits at y≈103 on the other for that same element. So the two

different places. Given that concentric ironing emits one continuous spiral, a difference in ring start

15 mm offset. The first run-order difference is at run index 251 (native `88.715 -> 83.269`, ares
