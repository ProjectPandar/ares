# Concentric ironing: `ironing_areas` ExPolygon emission order — discovery SPEC

Status: discovery record + proposed slice. Docs only: no source, no fixture, no
roadmap change.

## Problem

`ironing_pattern=concentric` is one of the two values the GUI and shipped
presets can produce (`PrintConfig.cpp:4298-4310`,
`enum_values = {rectilinear, concentric}`). With `ironing_type=top` on
`tests/parity/summary/time-cost.3mf` it is **not** byte-equal to Native.

Measured on main `9bbc63c9` (release build of that commit):

| oracle | Ares | Native | diff lines |
|---|---|---|---|
| seeded (`ORCA_REPLAY_SEED=0`) | 6,799,928 B | 6,799,948 B | 240 |
| official (canonical producer) | 6,799,928 B | 6,799,948 B | 240 |

Both oracles first differ at the same place (G-code line 257365): Native travels
to `X162.816 Y88.715` and irons the upper ring stack, Ares travels to
`X162.816 Y103.715` and irons the lower one.

### Fixture labelling (no masking needed)

The fixture sets `gcode_label_objects=0` — exactly the reachable value the
merged `alignedrectilinear` leg uses. With it, upstream emits the stable
`; start/stop printing object, unique label id: <n>` form instead of
`; printing object <name> id:<64-bit value>`, whose value varies per process.
With that setting the only run-to-run difference is the
`; generated by … on <timestamp>` line, i.e. exactly what the harness comparator
already normalises; no additional mask is introduced, and repeated Native runs
are byte-identical (verified: 0 diff lines between two fresh runs in each
oracle).

### Oracle determinism (both modes usable)

The official oracle **is** deterministic for this configuration when driven
through the canonical producer (`ARES_ORCA_BIN` = the official wrapper,
`ORCA_APPDIR`, `ARES_ORCA_NATIVE_BIN`, `ARES_ORCA_RESOURCES_DIR`; Native
parallelism 1). Repeated fresh runs with the harness comparator's normalisation (generator line
only):

- two fresh seeded runs: **0** differing lines;
- two fresh official runs: **0** differing lines.

An earlier note in this investigation claiming "official is non-deterministic"
was wrong: it came from invoking the native binary directly instead of through
the canonical wrapper environment, and from not separating `id:`/header lines
from geometry. No determinism problem is outstanding.

`ironing_angle=45`; `ironing_angle=30` + `ironing_angle_fixed=1`;

## What is established, and what is not

**Established by exact observation of the emitted G-code** (this is an exact
read of the per-area emission order, not an inference from travel):

- 1,243 concentric ring-stack blocks on both sides;
- the **multiset of blocks is identical** — same rings, same coordinates;
- identical **1,056-block prefix**;
- from block #1056 two same-shaped regions swap order:
  - Native #1056 = `(162.82, 83.27)–(168.26, 88.72)`, which appears in Ares at
    index **1214**;
  - Ares #1056 = `(162.82, 98.27)–(168.26, 103.72)` (same rings, dy = 15.00 mm),
    which appears in Native at index **1068**;
- only 16 of 14,584 ironing moves differ overall and all are relocating
  travel/link moves; the model time estimate shifts by 6 s.

**Not established: which intermediate vector first diverges.** The block order
proves the *per-area* order differs, but it does not by itself discriminate
between

1. `polys` accumulating in a different order (`Fill.cpp:1685-1697`
   `polygons_append` for top/bottom surfaces and, for `AllSolid`, the
   `stInternalSolid` appends), and
2. the order `intersection_ex` / the internal `union_ex` emits for the same
   input set (`Fill.cpp:1697`, `:1700-1702`),

because either can permute the final `ironing_areas` while leaving its content
unchanged. A previous draft asserted (2) from "pure permutation" alone; that
inference is invalid and is withdrawn here.

### Discrimination completed (which intermediate permutes first)

The G-code-order evidence above was not sufficient on its own, because
accumulation order and union output order both permute the same way. The
discriminator was obtained with temporary, uncommitted Ares instrumentation
(`ARES_IRON_AREA_DBG` at `fill_entities/ironing/areas.rs`, reverted; log
`evidence/ares-areas-order-instrumented.log`, analysis
`evidence/areas-order-analysis.txt`).

On the layer that the G-code diff shows reversed:

```
AREAS_IN  (accumulated areas = record.slices order)
  y sequence: +0.30, -14.70, -29.70, -29.70, -14.70, +0.30, +0.30, -14.70, -29.70   (mixed)
AREAS_OUT (Ares intersection_ex result = ironing_areas)
  y sequence: +0.09, +0.09, +0.09, -14.90, -14.90, -14.90, -29.90, -29.90, -29.90   (strictly Y-descending)
```

- Ares' produced order is **strictly Y-descending** and is **not** the input
  order (`OUT != IN`), so the permutation is produced by the
  intersection/union step, not by accumulation.
- Native irons the same two stacks in **Y-ascending** order (G-code
  `y=83.27` → model −32.7 before `y=98.27` → model −17.7).

Conclusion: the **first differing intermediate value is the ordered
`ironing_areas` vector**, and its owner is the clipper intersection/union
output ordering — upstream `union_ex` → `PolyTreeToExPolygons`
(`ClipperUtils.cpp:169-195`) — **not** `polys` accumulation
(`Fill.cpp:1683-1699`), and not `union_safety_offset` (not taken on this layer:
one region, no `stInternalSolid` fills).

Bounded scope of this conclusion: it decides *which* stage permutes. The exact
traversal rule that makes the ported engine emit the opposite direction is the
GREEN work. Reordering the result after the fact to match output is explicitly
forbidden; the fix must be in the ported traversal so the order falls out
naturally.

### Clipper1 ordering comparison (read-only, upstream `deps_src/clipper/clipper.cpp`)

The Clipper1 that Orca compiles is `deps_src/clipper/clipper.cpp`, included under
`Slic3r::ClipperLib` by `src/libslic3r/clipper.cpp`. The four order-bearing
places were compared line by line:

| role | upstream | Ares port | verdict |
|---|---|---|---|
| local-minima sort | `ClipperBase::Reset` `std::sort(m_MinimaList, lm1.Y < lm2.Y)` — Y ascending (`clipper.cpp:970-972`) | `minima.rs:28` `fixed_gcc_sort_by(&mut self.minima, a.y < b.y)` (Clipper1 policy `SORT_MINIMA_BY_X = false`, `round_policy.rs:32`) | same (Y ascending) |
| minima consumption | `InsertLocalMinimaIntoAEL` takes `m_MinimaList.back()` + `pop_back()` (`clipper.cpp:1492-1498`) | `minima.rs:54-60` `minima.last()` + `pop()` | same (largest Y first) |
| scanbeam | `std::priority_queue<cInt, cInts> m_Scanbeam` (`clipper.hpp:466-467`), default `less` = **max-heap**; `botY = m_Scanbeam.top()` then descending (`clipper.cpp:1109-1122`) | `engine.rs:200-203` `scanbeam.pop()`/`peek()` on a max-heap; same `botY`/`topY` loop (`engine.rs:170-186`) | same (max-heap, Y descending sweep) |
| output-ring creation | `AddOutPt` creates the OutRec on first `e->OutIdx < 0` (`clipper.cpp:2002-2017`); called from `InsertLocalMinimaIntoAEL` (`:1507`,`:1514`) and `AddLocalMinPoly` (`:1398-1444`) | `output/rings.rs:77-88` `create_out_rec` on first allocation; called from `insert_local_minimum` after `is_contributing` (`minima.rs:66-100`) | same shape |
| tree build | `BuildResult2` two passes over `m_PolyOuts`, append-only (`clipper.cpp:2801-2855`) | `polytree.rs:250-287` append by out_rec index | same |
| tree walk | `PolyTreeToExPolygons` root → holes → grandchildren recursion (`ClipperUtils.cpp:169-195`) | `polytree.rs:67-81` same recursion | same |

So the four candidate order sources are **not** where Ares differs, and the
earlier statement that "upstream is a min-heap" was wrong: the upstream sweep is
**Y-descending** (max-heap `top()`), exactly like Ares. The measured difference is
a different permutation *within* the sweep, i.e. which output rings get created
first for the same set of disjoint areas:

- Native order on the 9-area layer: grouped by **x** (largest x first), y
  descending inside each group, with the y direction alternating between groups
  (`(x=32.8,+0.3) (32.8,-14.9) (32.8,-29.9) (17.8,-29.9) (17.8,-14.9) (17.8,+0.3) …`);
- Ares order: grouped by **y** (`+0.09 ×3`, `-14.9 ×3`, `-29.9 ×3`).

This is now the open item: the specific rule that decides, for a single sweep
level, the order in which disjoint rings are created is still not pinned to a
source line. Candidates still to compare are the active-edge ordering used when
several local minima share one `botY` (`InsertEdgeIntoAEL`/`AEL` insert
comparator, `clipper.cpp:1492-1560` plus the `E2InsertsBeforeE1` tie-break at
`:2856-2870`) and the `ProcessIntersections`/`ProcessEdgesAtTopOfScanbeam`
sub-order. Per instruction, no fix will be attempted until that is located in
source; sorting the produced polygons afterwards is forbidden.

### Route (b) outcome: Native does not reorder after the clipper

The remaining question was whether Native's `ironing_areas` order is the clipper
scan order, or the `polys` input order (in which case a post-clipper reorder in
`Fill.cpp:1713-1731` or on the G-code side would be the culprit). Answered from
measurement, without needing a stack read on the stripped binary:

- Native's emitted order on the 9-area layer is **x-grouped, with y descending
  inside each group and the y direction alternating between groups**:
  `(x≈32.8, +0.3) (32.8, −14.9) (32.8, −29.9) (17.8, −29.9) (17.8, −14.9) (17.8, +0.3) (2.8, +0.3) (2.8, −14.9) (2.8, −29.9)`.
- The clipper sweep is Y-descending (max-heap `m_Scanbeam`, `clipper.cpp:1109-1122`),
  so a pure scan order for this set would be `y = +0.3, +0.3, +0.3, −14.9, …`
  i.e. y-grouped. Native is **not** y-grouped.
- Ares' `AREAS_IN` (proved position-for-position equal to Native's input order)
  has exactly the x-grouped/alternating structure Native emits.

So Native's `ironing_areas` follows the **input** order, not the scan order.
Because `Fill.cpp:1713-1731` is a plain `for (ExPolygon &expoly : ironing_areas)`
with no sort, and `eec->no_sort = true` (`Fill.cpp:1726`) forbids G-code-side
sorting, there is **no post-clipper reorder on the Native side**. Ares, by
contrast, *does* reorder (its `AREAS_OUT` is y-grouped).

Consequence: the deviation is inside the Ares clipper union/intersection output
ordering, not after the clipper — so route (b) resolves to route (a): compare
Ares' `create_out_rec` call order for this layer against the order the upstream
engine would produce. That comparison is the next step and needs the temporary
Ares instrumentation (or an equivalent runtime probe), which is not started
without approval.

## Upstream boundary (source-cited)

- `OrcaSlicer/src/libslic3r/Fill/Fill.cpp:1507` — `Layer::make_ironing()`.
- `:1617-1645` — `by_extruder` accumulation, `std::sort`, span scan (`j`).
- `:1683-1688` — `AllSolid` `stInternalSolid` appends into `infills`.
- `:1691-1698` — `if (!infills.empty() || j > i + 1) { append(polys, infills); polys = union_safety_offset(polys); }`
  (for this fixture: one region, one extruder, no solid-infilling appends, so
  this branch is **not** taken — worth confirming in the RED leg's own layer).
- `:1700-1702` — `ironing_areas_offset`, then
  `ironing_areas = intersection_ex(polys, offset(this->lslices, -ironing_areas_offset))`,
  which is `union_ex(intersection(subject, clip))`.
- `:1713-1731` — `Surface surface_fill(stTop, ExPolygon())` reused; per-area
  `f->fill_surface(&surface_fill, fill_params)`; one `ExtrusionEntityCollection`
  per area with `no_sort = true` (`:1726`), so G-code block order *is* loop
  order.

## Ares destination boundary

- `crates/ares-core/src/project_slice/fill_entities/ironing/areas.rs` —
  `ironing_areas()`: collects `record.slices` (Top, plus Bottom for
  `AllSolid`) in **record order**, appends `InternalSolid` fills when
  `AllSolid` and not `iron_completely`, unions only when such fills were added
  (`union_safety_offset_expolygons`), then
  `intersection_ex(&areas, &offset_expolygons(layer_slices, -inset))`.
- `crates/ares-core/src/project_slice/fill_entities/ironing.rs` — the
  `for area in ironing_areas` loop that appends one `FillExtrusionCollection`
  per area (the G-code block order).
- `crates/ares-core/src/geometry/clipper/*` — `union_ex` / `intersection_ex`
  ports whose output order feeds the loop.
