# Discovery: `hole_to_polyhole` region option — parsed but never applied

## Upstream source boundary

- `OrcaSlicer/src/libslic3r/PrintObjectSlice.cpp:847` — inside
  `PrintObject::slice_volumes`, calls `this->_transform_hole_to_polyholes()`
  after slice/replace steps, before `groupingVolumesForBrim`.
- `OrcaSlicer/src/libslic3r/PrintObject.cpp:189-~280`
  (`_transform_hole_to_polyholes`) — scans every `Layer->m_regions[r]->
  slices.surfaces` for `expolygon.holes` that are convex
  (`hole.convex_points(PI).empty()`), have `>8` points, and whose
  vertex-radius and edge-midpoint-radius variation stays inside
  `region().config().hole_to_polyhole_threshold` (default 0.01 mm).
  Matching holes that persist across >= 2 contiguous layers (or exist on
  layer 0) are replaced by `create_polyholes(center, diameter_max,
  scale_(nozzle_diameter), twist)` — a regular polygon sized for screw
  clearance. `hole_to_polyhole_twisted` rotates successive-layer
  polyholes.
- `OrcaSlicer/src/libslic3r/PrintConfig.cpp:7093-7120` — option defs:
  `hole_to_polyhole` (bool, default false), `hole_to_polyhole_threshold`
  (FloatOrPercent, default 0.01 mm), `hole_to_polyhole_twisted` (bool,
  default true). Defined upstream behaviour (geometry transform), not
  UB.
- Invalidation: `PrintObject.cpp:1201-1203` lists the three keys as
  slice-step invalidating; `Preset.cpp:1275-1277` lists them as
  "object" scope keys.

The gate `region().config().hole_to_polyhole` (`PrintObject.cpp:201`)
makes this a **region-scoped** option: each `LayerRegion` config is
consulted independently.

## Ares state

- `crates/ares-core/src/options/region_fields.rs` parses all three keys
  into `RegionOptions` (defaults: false / `FloatOrPercent::Float(0.01)`
  / true), and `options/config_export/orca_block_keys/first.rs` lists
  them for config export.
- No consumer exists under `crates/ares-core/src/project_slice/` — the
  transform is entirely unported. Parsed-but-unapplied, Native-accepted,
  non-UB.
