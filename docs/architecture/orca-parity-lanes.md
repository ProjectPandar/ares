# Orca parity lanes

An exclusive reference test must either run its comparison in the correct lane or not be selected. Returning successfully because the reference mode is wrong makes a test appear to pass without running its assertions. This is a harness contract; it changes no Native supplier, slicer behavior, or comparator.

## Selection and runtime checks

- `.config/nextest.toml` owns lane membership. `parity-official` excludes the 23 seeded-only `ares-cli::orca_parity` test identities; `parity-seeded` excludes `object_emission_cases::fuzzy_allwalls_rng_order::official_fuzzy_allwalls_oracle_is_explicitly_unstable`. Both preserve all other identities and the normal ignore policy. Use exact names scoped to the suite; do not rename or mark tests ignored to select a lane.
- Nextest intersects `-E` and name filters with the profile's `default-filter` (`cargo nextest list --help`, nextest 0.9.137). Both listing and execution must use the same profile. `--ignore-default-filter` bypasses this protection; use it only to test the runtime guard, not to collect parity evidence.
- At the runner's reference gate, `ARES_REQUIRE_ORCA=1` requires `ARES_PARITY_LANE=official` or `seeded`. The lane must agree with `ARES_PARITY_SEEDED_REFERENCE`: unset or `0` means official, `1` means seeded, and other values are invalid. Keep the seeded flag for existing producer, replay, and diagnostic consumers; it cannot stand in for the explicit lane. Missing or inconsistent configuration and execution of an exclusive test in the wrong lane must fail.
- Route ordinary and exclusive references through `runner/environment.rs` for the existing required-or-optional supplier checks. Exclusive cases also enforce the lane check. Mixed-contract tests keep their existing official and seeded assertions. This does not add an outer-lane requirement to standalone CLI probes or a new rule for per-case initialized replay suppliers.

## Case admission

The 23 ordinary case switches, including `ARES_PARITY_CLUSTER`, were enabled in both frozen reference environments. Remove them: nextest selection and runner availability decide whether the test runs. An unconfigured run without `ARES_REQUIRE_ORCA=1` has the same optional comparison behavior as other parity tests and makes no parity claim. A valid optional reference configuration can run a selected comparison without another switch. Remove the eight seeded-only case switches as well. The seeded lane and the existing per-case supplier, replay-seed, and comparison assertions already express their requirements.

Both standard parity profiles also exclude exactly `smoke::printer_sweep` and `stock_presets::sweep::tests::stock_printer_sweep`. The corresponding `ARES_PARITY_SWEEP=1` and `ARES_PARITY_STOCK_SWEEP=1` remain explicit opt-ins for deliberately selected sweeps outside those profiles. Selecting a sweep with Orca required and without its opt-in is a configuration failure. An ordinary optional run must not start a sweep by default. The targeted cluster check remains selected in both lanes.

The dedicated Tier 1 parity jobs supply the explicit lane and matching profile. They run selected cases with their existing Native suppliers, including the targeted cluster check. Other Tier 1 jobs and local runs without a configured oracle use the normal optional path; no CI-only behavior is added. The separate GLU test-time oracle uses shared required and optional supplier checks without the former profile-entry switch. Browser fixture consumers continue to select the same reference tests and supply the same launcher, resources, and artifact root.

## Batch migration

After the frozen run lands, set `ARES_PARITY_LANE` in each frozen parity environment and pass `--profile parity-official` or `--profile parity-seeded` to both preparation-time listing and execution. Retain the existing supplier paths, replay variables, runner, and pinning. Once the harness no longer reads the retired case switches, drop them from the new environment snapshots; don't change existing frozen snapshots. Neither standard parity lane enables a sweep. The browser fixture-producing run and compile-only checks do not switch profiles. Keep the orchestration outside this repository unchanged until that migration.

For incremental checks, use the corresponding lane profile on each side and add the existing task filter with `-E`; only entries with `filter-match.status == "matches"` are expected to produce terminals. Do not use `--ignore-default-filter`. If the base predates the profiles, either arrange an approved baseline replay on a profile-aware tip, or project the legacy inventory onto the same exact eligible identities and run the corresponding exact selection on the base. Do not count old no-op passes as comparison evidence. Record the selected IDs with each lane, separate intentional exclusions from test outcomes, and require exactly one terminal for each expected ID. Continue to protect baseline passes among eligible IDs; an unexplained missing result is not a lane exclusion. An intentionally empty scoped lane earns no parity credit.
