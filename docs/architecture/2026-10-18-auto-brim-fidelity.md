# AutoBrim fidelity notes

The AutoBrim implementation follows the upstream grouping and width boundaries. Volume grouping uses `PrintObjectSlice.cpp:517-660` and `:798-807`: only `model_part` volumes participate in positive groups, negative volumes are subtracted, and first-layer `lslices` are assigned to groups after simplified comparison while the original polygons are retained. The three safety offsets use Clipper's default miter limit 3 (`ClipperUtils.hpp:19-27`).

Width calculation follows `Brim.cpp:260-305` and `:497-527`: group height comes from the transformed model-volume mesh bounding box, the 2-D first-layer polygon box feeds the height-to-area term, group width is quantized before the `<5`/`1.5*thermalLength` decision, and the additional-width and bbox clamp are evaluated per polygon. Grouping resolution is the scaled print resolution used by `:798-803` without an extra clamp.

`Model::findMaxSpeed` (`Model.cpp:3222-3255`) starts with the global `printSpeedMap`; an object with no config keys returns its global maximum directly. With object keys, `inner_wall_speed` also scales external speed by the global external/internal ratio, and the remaining matching object keys override individual roles. The current region-speed carrier does **not** port this object-key-presence behavior. Object/volume-local speed overrides, the ratio rule, and the empty-key/global-zero edge are deferred, not covered by a new admission guard. The retained AutoBrim witnesses have no object/volume speed keys: their global role speeds are outer=40, inner=40, sparse=60, solid=50, top=30, support=40, and small-perimeter=50%. The resolved small speed is 20; `Model.cpp:2976-3010::setPrintSpeedTable` computes the global maximum from the other six roles (and does not load the global small-perimeter percent). None of the witnesses supplies an object-local small-perimeter key, so both paths supply the same sparse maximum 60. This is fixture equivalence, not a claim of general `findMaxSpeed` parity.

`Brim.cpp:120-148::getadhesionCoeff` is **object-wide**, not group-wide: collect external-perimeter extruders from first-layer regions with actual extrusions, then visit all object volumes in model order; the last matching volume with a material-table entry determines adhesion. Only `Model.cpp:3258-3280::getThermalLength` takes the minimum material reference over a group's volumes. The current group-filtered material carrier does **not** port object-wide adhesion across distinct material groups or first-layer extrusion eligibility; both remain deferred, without adding an Unsupported guard. Uniform-material witnesses are equivalent because every eligible matching volume has the same coefficient. The derived multi-volume witness is a geometry/thermal comparison only: its Native-active base and changed Brim signature do not establish cross-group adhesion parity. No claim of support for the general mixed-material boundary is made.

The modifier-volume witness was removed after Native-first probing: legal modifier inputs produced no `;TYPE:Brim`, so no active Native observable could distinguish grouping or adhesion. The retained multi-volume witness starts from the Native-active bump base and records a changed Brim block after adding a second volume.

The former PLA/PETG material-table whole-output case is excluded from this
slice's target set because its first difference is the pre-existing
GCodeProcessor M73 placement/time-estimator gap (Native `M73` precedes the
first Ares move; the same offset occurs on the pre-AutoBrim parent). The
AutoBrim grouping witness remains the multi-volume bump-base comparison.

## Review follow-up: geometry thermal cap

`Brim.cpp:289-303` names the bbox2 diagonal `thermalLength` and the group material-table minimum `thermalLengthRef`. The 1.5 multiplier and `<5 && <1.5*thermalLength` omission predicate use the **diagonal**, not the material reference; only the thermal-growth division uses the reference. RED′ will derive a 1×1×3 mm pillar from the existing project settings (global maximum speed 60). Its nondegenerate square moment is 1/12 mm⁴, giving the uncapped speed term 3.375 mm, whereas the geometric cap is 1.5√2 ≈ 2.121 mm. The old code omits 3.375 as `<5`; Native caps to 1.5√2 and retains it because equality fails the second strict-less-than condition. Height 3 is below the `groupHeight >10` additional-width gate, so that bump cannot hide the discrepancy. Native must emit Brim before strict API/CLI whole-output comparison; no Native output is committed.

The nondegenerate polygon second-moment path must retain upstream floating-point division semantics, not return zero on a zero moment or zero total area. An empty polygon collection follows the upstream failed-moment sentinel (`-1.e30` before coordinate scaling); no new fallback or admission guard is introduced. GREEN′ is restricted to production code for this geometric cap/omission and moment behavior. First-layer extrusion-eligible object-wide adhesion and object-key-aware speed lookup remain the explicit deferred adjacent boundaries above.
