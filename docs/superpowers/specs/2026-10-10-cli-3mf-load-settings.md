# CLI 3MF + `--load-settings`/`--load-filaments`: guard removal through the single composition

Status: proposed. Upstream pin `8500fcdccaa10b5099ac20d252af3a7c560046f1`.

## Problem

`ares-cli/src/main.rs` rejects `--load-settings`/`--load-filaments` with a
3MF input (`--load-settings with 3MF input is not supported yet`, exit 1).
Native supports the combination: the post-process load-settings witness runs
`--slice 0 --load-settings machine.json;process.json --load-filaments
filament-0.json --outputdir <dir> input.3mf` and returns **-19
`CLI_POSTPROCESS_NOT_SUPPORTED`** (exit 237, `result.json`
`post_process is not supported under CLI.`, empty stderr, no G-code),
because the **embedded** `post_process: [""]` is a non-empty array. Ares
currently exits 1 with the guard message.

## Upstream boundary (source-cited, pin `8500fcdcc`)

- `OrcaSlicer.cpp:1682-1690` — the 3MF load block rejects a non-empty
  embedded `post_process` (including `[""]`) with `-19` **before**
  load-settings processing (`:1953+`): the check is keyed to the 3MF
  input, not to the flags.
- `OrcaSlicer.cpp:1953-2215` — `--load-settings`/`--load-filaments`
  files load through `load_config_file` and become the
  machine/process/filament overlay source.
- `OrcaSlicer.cpp:2750-2812` — `update_full_config` overlays every key
  the loaded presets supply onto the 3MF's full-config base and keeps
  the rest.
- `Utils.hpp:44`, `cli_errors` (`OrcaSlicer.cpp:111-131`) — `-19` family
  channels; already ported (`SliceError::PostProcessNotSupported` →
  `ares-cli/src/failure.rs`).

## Rust destination

- `ares-core/src/profiles/entry.rs::with_load_settings_source`: the
  composite entry's `validate_print` becomes input-format-keyed —
  `true` for 3MF inputs (`InputFormat::detect`), `false` otherwise.
  This drives the existing `from_3mf_with_profiles` O5 gate: the
  **pre-overlay embedded** raw's `post_process` check runs before the
  `:2750-2812` overlay — the same single composition the web profile
  path uses; no parallel load path is created.
- `ares-cli/src/main.rs`: delete the 3MF extension guard; 3MF inputs
  flow into the existing `slice_with_load_settings` branch.

## E2E REDs (two cases)

Both run against the same argv shape as the witness and fail today on
the guard (exit 1):

1. **Rejection witness** (`load_settings_cli.rs`): pins the
   witness bytes (`input.3mf`, `machine.json`, `process.json`,
   `filament-0.json` under `tests/parity/validation/load-settings-3mf/`);
   Native (cached `cli-result` reference extended with the
   `--load-settings`/`--load-filaments` argv components) returns the -19
   family. GREEN = exit byte, stdout, stderr, `result.json` bytes, and
   no-G-code all identical.
2. **Positive compatible case**: removing the guard opens the forward
   slicing path, so a full-output byte comparison is mandatory. Fixture =
   the witness `input.3mf` repacked with the embedded `post_process`
   emptied (`["""]` → `[]`), keeping `machine.json`/`process.json`
   byte-identical: the loaded process's `compatible_printers` lists the
   loaded machine's system name (`"Creality Ender-3 0.4 nozzle"`, no
   `inherits`), so upstream branch 1 (`OrcaSlicer.cpp:2576-2585`)
   adjudicates compatible and Native slices. The derived
   `compatible-filament-0.json` pins the embedded `filament_colour`
   (`#F2754E`) so the loaded filament matches the project's own color —
   `OrcaSlicer.cpp:3392-3402` sets `filament_color_changed` on any color
   difference and `:4626` then re-places the model; pinning the color
   keeps the control on the overlay surface itself, with the
   color-change re-placement owned by the deferred arrange slice (it is
   not a divergence workaround). GREEN = the complete
   G-code output matches Native byte-for-byte under the existing
   banner normalization (`; generated by `).

**BLOCKED rule**: if the positive RED exposes output differences,
GREEN must close them within this slice; otherwise the slice is
BLOCKED and not merged (the guard stays).

## Addendum: `-5`/`-19` read-ordering slice (2026-10-11)

Upstream stage order: the 3MF load block admits the project first —
the embedded `post_process` gate (`OrcaSlicer.cpp:1682-1690`, `-19`)
fires during `load_3mf` — and only afterwards does the producer read
the `--load-settings`/`--load-filaments` files (`:1953-2024`, `-5`
`CLI_CONFIG_FILE_ERROR`). The Ares CLI adapter reads the preset files
before calling core, so a missing file shadows the `-19` rejection.

- **RED** (`orca_parity_load_settings_3mf_missing_file_post_process_order`):
  witness `input.3mf` (embedded `post_process [""]`) with
  `--load-settings <absent machine.json>;<real process.json>` and the
  witness `--load-filaments` list. Native references the argv with a
  new `EarlyExit::MissingSettingsFile` runner kind (absent settings
  entries enter the cache identity as an `absent:<name>` marker, argv
  keeps the raw path); expected native outcome is `-19`/exit 237
  because the 3MF admission precedes the file reads. Ares today exits
  1 (legacy `Loading setting file … failed`) — the ordering RED.
- **GREEN** (adapter-ordering only): before `read_preset_files`, the
  CLI adapter probes 3MF admission through a thin public core entry
  `validate_load_settings_input` that composes `load_project` with the
  existing `validate_post_process` gate — the same O5 check the
  composite slice entry runs; no new pipeline branch, error mapped by
  the existing `slice_error_to_failure` (keeps exit 237 and the exact
  `-19` channels). Files present + clean 3MF keep the existing
  behavior.
- **Deferred** (not this slice): `-5` exit fidelity for the clean case
  (native `-5`/251 family vs the adapter's legacy exit 1) — separate
  CLI failure-mapping slice; the control for it stays out until that
  slice lands.
