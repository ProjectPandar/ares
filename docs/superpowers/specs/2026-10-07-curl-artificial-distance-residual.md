## Acceptance contract (non-negotiable)

The acceptance test is a **whole-file byte compare** of the emitted
plate gcode against the seeded oracle, normalizing **only** the
`; generated by` banner line — the same normalization already used by
`crates/ares-cli/tests/orca_parity/narrowed_x2d_whole_file.rs`.

No comparator exemptions for M73 placement, E last-digit, or any other
class. Every residual diff hunk must either:

- be eliminated by this slice, or
- be proven **native nondeterminism** — i.e. demonstrate that the
  same raw upstream binary produces different bytes for that hunk
  across repeated runs of the same input; then it is documented with
  the repro runs as evidence, or
- be attributed to an independent Ares bug outside the cited upstream
  boundary — then it becomes its own slice or is fixed here.

## Investigation result (2026-10-07) — root cause localized OUTSIDE curl geometry

White-box check: ares' `artificial_distance` reproduces orca's
`art`/`nr` values **exactly** when fed orca's stored CurledLine set
(fixture `oracle_artd_sermoon_v1.txt`, test
`artificial_distance_matches_the_sermoon_v1_oracle_records` —
green on first run; H1/H4 ruled out for the formula itself).

Local probes (env-gated, uncommitted, reverted) then showed:

- ares' `previous_curled` set at layer 2 = **5 whole-edge lines**
  (h 0.30-0.48) vs orca's ~19 junction-level lines. The degenerate
  corner line (4.645,4.645)-(4.645,4.645) reaches h=0.4761 vs
  orca's 0.0561/0.1503 — producing art=0.1179 vs orca's 0.0743
  (crosses the 13% band edge → F6120 vs F6818.82).
- Reason: ares' stored `ExtrusionLoop.paths` polyline for this wall
  = **5 points** (4 corners + close) while upstream's stored entity
  = **~15-19 points at 1.1612mm junction spacing** — confirmed both
  by orca's CURL/ARTD dumps and by ares' own emitted path points
  (the scarf `detail()` subdivision reproduces the same 1.1612
  positions: 9.29mm edge / 8). 
- ares' pre-simplify Arachne `ExtrusionLine` = **9 junctions**
  (4 corners + 4 edge midpoints, uniform width 567079) → simplify
  legitimately removes 4 → 5. Upstream's junction set contains the
  ~1.16mm spaced junctions, i.e. **ares' Arachne beading/
  SkeletalTrapezoidation emits fewer junctions than upstream**
  (upstream `WallToolPaths.cpp:491,545-553` passes
  `discretization_step_size = scaled(0.8)` into the wall maker;
  SkeletalTrapezoidation.cpp:167-302 discretizes edges).

Consequence: the residual is NOT in the curl pipeline at all — it
is in the Arachne junction density of the stored perimeter entities.
That is a new upstream-cited boundary
(`SkeletalTrapezoidation.cpp::discretize`, `WallToolPaths.cpp::
generateToolpaths`) rather than the `ExtrusionProcessor.hpp` /
`AABBTreeLines` boundary this spec scoped. The implementation slice
must be re-planned around that boundary; the curl white-box test
lands as evidence that the curl path itself is at parity.

## The open delta (what this slice must resolve)

Orca's `ART` records show `art=0.0743` for
`seg=(4.597,4.645)-(3.484,4.645)` yet emitted `spd=113.647 mm/s`
(= F6818.82, the no-slowdown band), while ares emits F6120 for the
same segment — consistent with ares computing a slightly larger
artificial distance (~0.081) that crosses the 13%-of-width band edge
(0.075/0.61 = 12.3% vs 0.081/0.61 = 13.3%). From the dump, the
decisive curled line is the right-edge vertical
`(4.645,-4.645)-(4.645,4.645)` at h=0.3003, d²=3.66e11 (d≈0.605 mm)
— exactly reproducing orca's `art=0.0743`. Ares either admits a
different candidate set or computes a different distance to it.

Hypotheses to prove or rule out, in order — each must be explicitly
dispositioned (confirmed / ruled out) in the implementation commit
message or the slice's evidence notes:

1. **Band-edge threshold drift (H1)**: ares' `art` for the diverging
   segments is only marginally larger than orca's (≈0.081 vs 0.0743)
   but crosses the 13%-of-`path.width` band edge
   (`overhang_overlap_levels`, `calculate_speed`), so a small distance
   difference flips the emitted F. Confirmed by the dump: orca's
   `art=0.0743` from the right-edge vertical line
   `(4.645,-4.645)-(4.645,4.645)` at d≈0.605. If ares' candidate set
   is identical but its `distance_from_curled` to that line differs
   (scaled-middle truncation, segment clamp), H1 is the root cause
   and the fix is in the distance measure (hypothesis 4 below).
2. **Second-pass CurledLine roll-in (H2)**: orca's ARTD shows `nr`
   for the same geometric seg dropping 3→2 between dump records —
   `next_curled_extrusions` rolls into `prev_curled_extrusions`
   (`ExtrusionProcessor.hpp`, `prev_curled_extrusions[object] =
   next_curled_extrusions[object]`) mid-layer, so the second
   `estimate()` pass on the same path sees a different set than the
   first. Ares' two-pass estimate must see the same rolled set at the
   same pass boundary; a roll-timing difference changes which curled
   lines are candidates.
3. **`all_lines_in_radius` membership**: upstream `nr` for each
   diverging segment is known from the ARTD dump (e.g. `nr=3` for the
   seg above); ares' candidate set must match exactly. The tree query
   compares `distance² ≤ radius²` (`AABBTreeLines.hpp:222-236`,
   `all_lines_in_radius` passes `radius*radius`).
4. **The len>2 projected-length filter** (`ExtrusionProcessor.hpp:
   388-402`): `projected_lengths_sum < 0.4·len` clears the candidate
   set — box corners `curr ± right·dist_limit`, `right` perpendicular
   of unit dir; `intersection_ln` clipping must match.
5. **`distance_from_curled` measure**: `line_alg::distance_to(line,
   new_scale(middle))` on **scaled** int coordinates vs ares'
   `segment_distance_scaled` — middle is truncated to scaled ints
   before the distance (`Line.hpp:43-70`, f64 projection clamped to
   segment).
