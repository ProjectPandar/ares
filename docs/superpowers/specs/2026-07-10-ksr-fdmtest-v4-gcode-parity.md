# KSR FDM Test V4 3MF-to-G-code Parity Spec

## Goal

Make Ares slice
`tests/ksr_fdmtest_v4/ksr_fdmtest_v4.project.3mf` into output that is
byte-for-byte equal to
`tests/ksr_fdmtest_v4/ksr_fdmtest_v4.gcode`, except for the single generator
name/timestamp line defined below. The implementation must be reusable for
future 3MF projects whose options differ.

This spec implements ARD-0023. It is complete only when the final golden test,
workspace tests, formatting, lint, and WASM checks all pass.

## Evidence baseline

The user-provided fixture is committed under `tests/` and is authoritative
input/reference data:

- 3MF size: 183,007 bytes.
- Reference G-code size: 6,339,134 bytes.
- Reference SHA-256 before normalization:
  `10aec9a156849f59929b578429a764a61453996a5834056f600c0adbb5d6a1b3`.
- 3MF SHA-256:
  `698f40f13c9075b818abedd3d10f022fbb5d8200aed48fbdde651f6bfb21b8a9`.
- 3MF package: 15 entries, including a root model, one object-model part,
  `Metadata/project_settings.config`, `Metadata/model_settings.config`, plate
  metadata, and previews.
- Mesh: 6,109 vertices, 12,234 triangles, local bounds
  `[-37.5,-35,-46]..[37.5,35,46]`.
- Root build transform places the instance at
  `(133.039205,115.992105,46)`.
- Embedded project configuration: 653 keys.
- Reference output: 269,330 lines, 460 `CHANGE_LAYER` blocks, final Z 92 mm.

The current Ares `InputFormat::ThreeMf` loader returns an empty model, and the
CLI requires an external `--options` JSON file. These behaviors contradict the
target and must be replaced for project slicing.

Both fixture files will be committed directly to this Git repository, without
Git LFS or an external download. A normal clone must provide their exact bytes
to local and CI tests. The golden harness verifies both SHA-256 values before
slicing so an accidental fixture change fails with a bounded diagnostic.

## Public boundaries

### Core project API

Add an in-memory project entry point in `ares-core`:

```rust
pub async fn slice_project(
    project: impl AsRef<[u8]>,
    metadata: GenerationMetadata,
) -> Result<Vec<u8>, SliceError>;
```

`GenerationMetadata` carries only non-option execution metadata needed for the
generator line, including the current local timestamp supplied by an adapter.
It must provide a deterministic constructor for tests. It may not carry slicer
options or fixture identifiers.

Keep the existing `slice(input, SliceOptions)` entry point for explicit-option
STL/API callers. It must not be used by the 3MF golden test, and passing
external options to project slicing is impossible by API construction.

### CLI and WASM

- CLI project form: `ares slice -o <output> <project.3mf>` with no required
  `--options`.
- STL form may continue to require `--options` while that public path exists.
- Supplying `--options` with a 3MF project must fail with a clear boundary
  error rather than silently overriding or ignoring it.
- `ares-wasm` exposes a byte-oriented project slicing binding and supplies
  generation metadata without filesystem access.
- A committed headless-browser harness must import the generated
  `wasm-bindgen` JavaScript module, pass the fixture as a browser
  `Uint8Array`, await the exported project-slicing function, and receive the
  generated G-code bytes through that JavaScript boundary. Calling only a
  Rust helper compiled for `wasm32` does not satisfy this boundary test.
- The stable JavaScript `sliceProject` export and browser harness land with
  the project-domain increment. Until project G-code is complete, the core
  returns a dedicated `ProjectSlicingIncomplete` error and the browser smoke
  test asserts that exact mapped error after passing the real fixture through
  JavaScript. Each later increment keeps that browser smoke green. The final
  increment removes the temporary error and changes the same browser test to
  the full normalized byte comparison.

## Project loader requirements

1. Read ZIP bytes entirely through an in-memory reader compatible with WASM.
2. Deserialize `[Content_Types].xml` into `ContentTypes`, `_rels/.rels` and
   `3D/_rels/3dmodel.model.rels` into `Relationships`, and validate their typed
   content types and relationship roles.
3. Parse root and object `.model` parts with namespace-aware XML handling.
4. Parse vertices and triangle indices without lossy `f32` conversion.
5. Resolve nested component paths and object IDs.
6. Compose component and build transforms in Orca order.
7. Preserve object, volume, instance, printable, auto-drop, and plate metadata
   needed downstream, including model label ID 133.
8. Parse `model_settings.config` object/part/assemble metadata.
9. Parse `project_settings.config` as the embedded project configuration.
10. Parse `slice_info.config` into `SliceInfo`, `filament_sequence.json` into
    `FilamentSequences`, and `plate_1.json` into `PlateJson`. `plate_N` is a
    dynamic member name with a typed `PlateId` key and `PlateFilamentSequence`
    value, not a dynamic JSON value.
11. Treat preview PNG entries as opaque deferred assets: validate their package
    paths and archive limits, but do not decode their payloads because no
    required G-code behavior consumes them.
12. Reject malformed archives, missing referenced parts, invalid indices,
    non-finite coordinates/transforms, and unsupported required extensions at
    this untrusted-input boundary.
13. Use serde against the named JSON/XML wire structs. Do not deserialize into
    `serde_json::Value`, another library's dynamic `Value`, `RawValue`, a DOM
    node tree used for runtime type tests, or a custom erased-value equivalent.
14. Apply these archive limits before allocating expanded buffers:
    - at most 4,096 entries;
    - at most 256 MiB expanded bytes for one entry;
    - at most 1 GiB total expanded bytes;
    - at most a 1,000:1 expanded/compressed ratio for non-empty compressed
      entries;
    - reject encrypted entries, unsupported compression methods, CRC failures,
      and conflicting size metadata.
15. Normalize entry names and relationship targets as OPC package paths in
    memory, independent of host filesystem rules. Resolve a leading `/` from
    package root, resolve legal relative targets from the owning part, and
    reject drive/UNC syntax, NUL, backslash ambiguity, empty interior segments,
    decoded `.`/`..` traversal, percent-encoded separators or dot-segments,
    fragments where a part path is required, and duplicate normalized paths.
16. Bound each XML or JSON text document to 64 MiB, XML nesting to 256 levels,
    attributes to 1,024 per element, and accumulated decoded XML text to 64 MiB.
    Reject XML DTD, external entity, general entity declaration/reference, and
    expansion constructs before serde consumption. Namespace declarations and
    ordinary escaped XML character references remain supported.
17. Add negative tests for every limit/rejection class using small synthetic
    archives: entry count, per-entry/total size, compression ratio, encryption
    or unsupported method where the ZIP library permits construction, CRC/size
    mismatch, absolute-host/traversing/encoded/duplicate paths, excess XML
    depth/attributes/text, DTD/entity payloads, malformed typed JSON/XML, and
    missing relationship targets.

## Configuration requirements

1. Define a concrete field for every one of the 653 embedded project keys and
   preserve their serialized ordering requirements. Split fields into the
   concrete config-group structs named in the destination map.
2. Deserialize Orca scalar, vector, percent, float-or-percent, enum, point,
   nullable, string, and G-code string forms into concrete field or wrapper
   types. Tagged enums are allowed only when they model an actual Orca union or
   enum option; a catch-all dynamic value enum is forbidden.
3. Associate values with printer, print, object, region, filament, and extruder
   scope where runtime semantics depend on scope.
4. Apply `PrintConfigDef::handle_legacy` and composite normalization relevant to
   the fixture before typed access.
5. Reproduce active extruder/filament selection and variant mapping. For
   example, eight-entry source vectors may become two active values in the
   exported config.
6. Reproduce `normalize_fdm*` effects. The embedded
   `enable_prime_tower = 1` must normalize to the single-material output state
   used by the reference rather than being copied blindly.
7. Export the exact effective config block, including key order, delimiters,
   quoting, escaping, vector separators, normalized values, and blank values.
8. Add a focused RED/GREEN test for every newly consumed behavioral option.
   A test must show output or typed runtime state changes when that option
   changes; source text assertions do not satisfy this requirement.
9. Options present but inactive in this fixture may remain retained-only until
   a future test activates them, provided their exact config-block
   serialization is implemented.
10. No defaults may be chosen from the fixture filename, reference G-code, or a
    fixture-specific conditional.
11. Unknown JSON option keys fail deserialization with the key name. Supporting
    a future key requires adding its concrete typed field and focused tests;
    unknown fields may not be retained in an untyped side map.
12. `SliceOptions` and all project/effective configuration structs must derive
    or implement serde directly. Known fields may not use production
    `serde_json::Value`, `serde_json::Map`, `RawValue`, `Box<dyn Any>`, or
    equivalent erased-value storage or runtime type branching.
13. Legacy key names are known typed inputs: express simple aliases with serde
    `alias`, and match complex legacy names in the custom serde visitor before
    the unknown-key branch. A legacy value is deserialized directly into the
    canonical field's typed wire form, then normalized; it is never parked in
    an untyped container. Only keys unmatched after canonical and legacy alias
    dispatch are rejected as unknown.
14. A genuinely open production JSON field is exceptional. It requires a
    source citation proving the upstream field is open-ended, a named containing
    struct and field, an entry in `scripts/dynamic_value_allowlist.toml`, and a
    reviewer-approved reason. Its dynamic payload may be preserved or emitted
    but may not be pattern-matched to choose an Option type or slicing branch.
    No such exception is currently required for the 653 fixture options.

## G-code requirements

1. Reproduce relative-E Marlin command semantics, formatting precision,
   omitted leading zero conventions, feedrates, accelerations, jerk, travel,
   retraction, spiral lift, wipe, fan, temperature, role changes, layer markers,
   object labels, and end commands exercised by the fixture.
2. Render machine, filament, layer-change, timelapse, and end custom G-code from
   embedded templates using Orca-compatible placeholder and conditional
   semantics. Template text comes only from the 3MF configuration.
3. Reproduce executable/config/header block placement and whitespace.
4. Reproduce filament length, volume, mass, cost, and all footer statistics.
5. Reproduce `GCodeProcessor` time estimation so the model time, total time,
   first-layer time, progress commands, and related metadata match exactly.
6. The generated line must have this shape:

   ```text
   ; generated by Ares 2.4.2 on YYYY-MM-DD at HH:MM:SS
   ```

   Ares compatibility metadata uses the target Orca behavior version `2.4.2`,
   independently of the crate package version.

## Golden test contract

Create a repository-level E2E test that:

1. Reads the project and reference files from `tests/ksr_fdmtest_v4`.
2. Calls the Ares project API or CLI without an external options file.
3. Asserts the reference contains exactly one line matching
   `^; generated by OrcaSlicer 2\.4\.2 on \d{4}-\d{2}-\d{2} at \d{2}:\d{2}:\d{2}$`.
4. Asserts Ares contains exactly one line matching
   `^; generated by Ares 2\.4\.2 on \d{4}-\d{2}-\d{2} at \d{2}:\d{2}:\d{2}$`.
5. Replaces each complete generator line with the same sentinel.
6. Compares the remaining byte arrays exactly.
7. On mismatch, reports the first differing byte/line and bounded context; it
   must not emit the full 6.3 MB files into test output.
8. Does not normalize time estimates, numeric formatting, whitespace, line
   endings, config values, ordering, or trailing bytes.
9. Never makes the reference G-code available to production runtime code.

The complete CLI golden test is executed once in RED before implementation.
Until the CLI adapter can satisfy it, it is committed with an explicit
`#[ignore = "full project parity incomplete"]`. Progress evidence follows the
actual stage boundary instead of requiring bytes that do not yet exist:

- before the public project API exists, manually run the ignored CLI golden
  and record its bounded missing-project-dispatch error;
- after the stable project API/browser export lands and through the last
  pre-output increment, keep the active headless-browser test green against
  the exact mapped `ProjectSlicingIncomplete` error for the real fixture;
- when the complete post-processed document first exists internally, compare
  it with the reference using the bounded first-difference helper;
- when the public core and browser paths are completed, require their exact
  normalized byte comparison; and
- remove the CLI ignore when the CLI adapter is completed and require the same
  exact comparison there.

No intermediate task emits approximate G-code merely to create a diff. All
increment-specific RED/GREEN behavioral tests are active and must pass before
their commits; CI is never made green by weakening an active assertion or
adding additional normalization.

## Source-level pinning cleanup

Remove a test when its asserted subject is only a raw Orca source line, token
sequence, neighboring milestone boundary, `source_file`, `source_lines`,
`raw`, dependency role, or `deferred_behavior`, and it does not vary runtime
input to observe Ares behavior. This test-intent rule applies even when the
test sits beside retained runtime code; remove only the pinning test in that
case.

Delete a private production module only after the test cleanup when both are
true:

- it implements no retained runtime option, slicing, or G-code behavior; and
- no non-test runtime path reaches it.

A mixed module is split only as needed to remove pinning declarations while
preserving its runtime code and behavioral tests.

Retain:

- option registry entries used for deserialization or validation;
- runtime parsers, normalizers, and consumers;
- behavioral tests that vary input and observe runtime/output behavior;
- concise source citations in this spec, plans, ARDs, and focused code comments;
- retained behavior, registry, and architecture documents; source-line-only
  Option milestone documents are removed with their pinning scaffolds.

The cleanup must cover the obsolete `PrintConfig.hpp`/`PrintConfig.cpp`
source-line corpus and equivalent source-line-only staged `PrintApply` tests,
without deleting real `print_apply` behavior.

The cleanup also removes the current `SliceOptions` unknown-key preservation
behavior and replaces it with typed serde round-trip, missing/default,
invalid-type, unknown-key, legacy-alias, vector-cardinality, and
effective-normalization tests. Tests may use `serde_json::Value` or `json!` as
test data when useful; production parsing and runtime behavior still consume
only concrete structs and typed fields.

## Implementation increments and review gates

Implementation is split into independently reviewable increments. The detailed
plan may split these further but may not merge them into one unreviewable diff:

1. Golden harness and pinning cleanup.
2. In-memory 3MF package/model/metadata loading.
3. Embedded typed configuration and effective-config normalization.
4. Orca-compatible coordinate and polygon kernel plus layer slicing.
5. Layer surfaces, classic perimeters, shells, infill, gap, and brim behavior.
6. Path ordering, extrusion, travel, retraction, speed, acceleration, and fan
   behavior.
7. Custom G-code/placeholders, config/header/footer serialization.
8. G-code post-processing, time estimation, statistics, and final byte parity.

Increment 3 is an umbrella and must be split in the plan at least by concrete
config group (printer, process, filament, object, region, and G-code), followed
by separate effective normalization/export and consumer-migration tasks. Each
sub-increment has the same dual-review, docs, verification, commit, and push
gate as a top-level increment.

Each increment follows TDD, is implemented by a fresh bounded subagent, is
implemented through the `sdd-workflow` and
`superpowers:subagent-driven-development` skills, and is reviewed independently
by both a fresh Codex reviewer subagent and OpenCode's default model. The gate
passes only if both return a literal `VERDICT: APPROVE`. Any `REVISE` or missing
verdict causes fixes and a complete re-review by both reviewers. User approval
does not replace either reviewer. After the dual approval, update relevant
roadmap/architecture status, run fresh verification, then create a Conventional
Commit and push it before starting the next dependent increment. Parallel
implementation is allowed only for tasks with disjoint file ownership and no
unmet dependency; each parallel task still receives its own dual approval,
docs update, verification, commit, and push.

## Error handling and performance

- Validate archive/XML/config data at public untrusted-input boundaries.
- Internal geometry and planning functions trust validated typed invariants and
  do not add speculative defensive branches.
- Avoid whole-file text copies where streaming/borrowed archive reads suffice.
- Avoid quadratic triangle, segment, or path scans where Orca uses indexed or
  ordered structures.
- Keep modified Rust files at or below 400 LOC by splitting along the upstream
  responsibility boundary.
- Core code remains free of filesystem, terminal, UI, OpenGL, and native-only
  dependencies.
- Known production structures and options under `ares-core`, `ares-cli`, and
  `ares-wasm` contain no dynamic serde value/map/raw-value, custom catch-all
  value enum, or erased option payload. Tests are exempt. A genuinely open
  production field is allowed only through the reviewed allowlist rule above,
  and its payload cannot control option typing or slicing behavior.

## Safety and rollback

- Each increment is an atomic reviewed commit on the parity feature branch.
- If an approved increment causes an unforeseen regression, rollback is a Git
  revert of that whole increment followed by the same verification matrix.
- No live runtime fallback, duplicate slicer, feature flag, or reference-output
  path is introduced for rollback.
- The public project API is allowed to return a typed not-yet-supported error at
  intermediate commits, but it may not emit approximate project G-code and may
  not be declared complete until increment 8 removes the golden-test ignore.

## Verification requirements

Every approved implementation increment runs the focused RED/GREEN tests plus:

- `cargo fmt --check`
- `cargo nextest run --workspace`
- `cargo clippy --workspace --all-targets -- -D warnings`
- `cargo check -p ares-core --target wasm32-unknown-unknown`
- `cargo check -p ares-wasm --target wasm32-unknown-unknown`
- `git diff --check`
- touched Rust LOC audit
- `cargo nextest run -p ares-core no_unapproved_dynamic_values`

Starting with the project-domain increment, the matrix also builds the
generated `wasm-bindgen` web package and runs the committed JavaScript harness
in headless Chromium. Before final parity it must pass the real 3MF bytes to
`sliceProject` and receive the exact mapped `ProjectSlicingIncomplete` error;
after final parity it must receive G-code bytes and apply the same single-line
normalization and byte-for-byte comparison as the native golden. A Rust-only
`wasm32` test or compile check is not a substitute for this browser gate.

The dynamic-value audit parses Rust syntax and detects direct, grouped,
renamed, and re-exported serde JSON Value/Map/RawValue imports and paths;
`from_value`; `json!` in production items; generic `ConfigValue`; erased
`Box<dyn Any>` payloads; and configured DOM/runtime-type patterns. It excludes
test files and `#[cfg(test)]`/`#[test]` items. Increment 1 records every existing
production occurrence as a normalized syntax fingerprint in
`scripts/dynamic_value_baseline.txt`. Subsequent increments must introduce no
new fingerprint and remove baseline entries for every owned module they
migrate. The baseline may only shrink. Separately,
`scripts/dynamic_value_allowlist.toml` contains only reviewer-approved,
source-cited genuinely open fields with exact path, containing struct, field,
and rationale. Increment 8 requires the migration baseline to be empty and the
full-tree audit to pass; approved open-field entries, if any, remain visible and
may not be used for runtime type or slicing dispatch.

Tier-1 native evidence is provided by a committed CI matrix on
`windows-latest`, `macos-latest`, and `ubuntu-latest`. Each matrix job checks
out the committed fixtures and runs `cargo nextest run --workspace` plus
`cargo clippy --workspace --all-targets -- -D warnings`. Formatting runs once
on Linux. A separate job installs `wasm32-unknown-unknown`, builds the
`wasm-bindgen` web package, runs both WASM checks above, and—once the stable
project export exists—executes the browser harness in headless Chromium. An
increment is not portable-approved until all required matrix jobs for its
pushed commit are green; local Windows results alone do not prove macOS,
Linux, or browser-WASM support.

The final increment additionally runs the full native and headless-browser
golden E2E comparisons and records their common normalized output hash in test
diagnostics or verification notes.
It also runs the original OrcaSlicer v2.4.2 project export against the same 3MF
in a temporary output location and verifies that the supplied reference is an
Orca-produced baseline under the same one-line normalization rule.

## Acceptance criteria

1. Ares loads the supplied 3MF project from bytes and obtains all geometry,
   transforms, object metadata, plate metadata, and options without external
   JSON or filesystem access in `ares-core`.
2. The project produces 460 layers through real geometry and config behavior.
3. Effective config normalization and config-block serialization match the
   reference exactly.
4. All geometry, toolpaths, G-code commands, custom templates, statistics, and
   time estimates match the reference exactly.
5. After normalizing only the two validated generator lines, Ares and reference
   G-code byte arrays are equal.
6. Production code contains no reference-G-code read, fixture-name/hash branch,
   copied toolpath payload, Orca executable invocation, FFI fallback, or legacy
   alternate slicer path.
7. Obsolete source-level pinning tests and their unreachable private modules are
   removed, while runtime option and slicing behavior tests remain.
8. Core and CLI remain portable across Windows, macOS, and Linux, and the
   generated `wasm-bindgen` JavaScript module processes the committed 3MF in
   headless Chromium and returns the same normalized G-code bytes.
9. Every spec, plan, and final implementation review gate receives literal
   `VERDICT: APPROVE` from both an independent Codex subagent and OpenCode.
10. Approved implementation increments update docs, pass required verification,
    and are committed and pushed using Conventional Commits.
11. A final original-OrcaSlicer v2.4.2 E2E export confirms the supplied
    reference baseline before Ares parity is declared complete.
12. A fresh clone and the committed Windows/macOS/Linux/WASM CI matrix obtain
    the two hash-pinned fixtures without LFS or external provisioning and pass
    their required jobs.
13. The dynamic-value migration baseline is empty; the syntax-aware production
    audit has no unapproved dynamic/erased-value dispatch; every approved
    genuinely open-field exception is source-cited and non-behavioral; and
    tests prove `[Content_Types].xml`, both relationship documents, both model
    documents, `model_settings.config`, `project_settings.config`,
    `slice_info.config`, `filament_sequence.json`, `plate_1.json`, and all 653
    known project options deserialize through concrete structs, typed maps,
    wrappers, and actual option enums. Preview PNGs remain explicitly opaque.
14. Archive/XML/JSON limit and path/entity negative tests prove the untrusted
    project boundary rejects bounded-resource and ambiguity attacks before
    unbounded allocation or semantic parsing.

Deferral does not permit omitting any option, geometry branch, formatting rule,
